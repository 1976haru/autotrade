# 연패 차단(circuit breaker) 검증 설계 + 백테스트

> Read-only 분석. 봇/주문 경로/설정 파일 변경 0줄.  
> 산출일: 2026-07-09. 데이터: 기존 35종목 1년 intraday corpus.

## 결론

**판정: (a) 연패 차단은 넣을 가치가 있다. 단, 새 장치를 만들기보다 기존 `ConsecutiveLossRule` 골격을 유한 cooldown 방식으로 활성화하는 쪽이 맞다.**

- reversal 함정은 이번 데이터에서 보이지 않았다. 5연패 뒤 다음 1개 거래 승률은 `20.0%`, 다음 5개 거래 승률은 `16.3%`로, 기준 승률 `39.86%`보다 훨씬 낮다.
- 5연패 뒤 다음 5개 후보를 쉬는 규칙은 최우수 후보 흐름에서 누적 손익을 `-6673.67%p -> -1800.06%p`로 개선했다. 개선폭은 `+4873.61%p`.
- 3패가 순손익만 보면 더 빠르지만 너무 자주 작동한다. 7/10패는 더 정밀하지만 손실을 너무 늦게 막는다. 운영 임계값은 **5패**가 가장 균형적이다.
- 현재 일일손실가드와는 중복이 아니다. 일일손실가드는 금액 기준 account guard이고, 연패 차단은 시장/신호 열화 감지 기준이다. 다만 코드에는 `consecutive_loss_limit` 규칙이 이미 있으므로 같은 기능을 새로 또 만들면 중복이다.

## 1. 현재 방어장치

| 장치 | 현재 상태 | 연패 차단과 관계 |
|---|---:|---|
| `max_daily_loss` | 기본 `200,000`원. `route_order`가 주문 평가 직전 `compute_today_realized_pnl(db)`로 실현손익을 재계산한 뒤 `RiskManager`가 차단 | 금액 기준. 연패 수 기준이 아니므로 직접 중복 아님 |
| `DailyLossLimitRule` soft 단계 | `daily_loss_warn_pct`, `daily_loss_reduce_pct` 필드는 있으나 기본 0 | 보조 경고. 기본 비활성 |
| `weekly_loss_limit` | `RiskPolicy` 필드는 있으나 기본 0 | 비활성 |
| `consecutive_loss_limit` | `RiskPolicy`와 `ConsecutiveLossRule` 존재. `route_order`도 활성 시 `count_consecutive_losing_trades(db)`를 주입 | **연패 차단 골격은 이미 있음. 기본 설정 경로에서는 꺼져 있음** |
| `auto_stop_consecutive_rejections` | 연속 `REJECTED` 주문이 N번 나오면 emergency stop | 주문 거절 반복 방어. 손실 거래 연패와 다름 |
| OrderGuard cooldown/duplicate/pending | 중복 주문, symbol cooldown, pending 차단 | 주문 흐름 방어. 손익 기반 아님 |
| KIS paper daily buy limit / max orders | 일일 매수금액 기본 300만원, KIS paper auto 주문수 기본 10 | 노출 한도. 연패 신호 감지는 아님 |
| emergency stop / AI kill switch | hard stop | 수동/시스템 비상정지. 연패 차단보다 상위 |

주의점: 기존 `consecutive_loss_limit`은 "한번 켜지면 어떤 조건으로 다시 푸는가"가 명확하지 않다. 실제 적용 시에는 **무기한 차단이 아니라 `N패 -> 다음 M개 BUY 후보 skip -> streak reset` 같은 finite cooldown**이 필요하다.

## 2. 분석 방법

기존 검증 체계와 맞추기 위해 `strategy_council_backtest` + `timeframe_sweep`의 forward-return 신호열을 그대로 재사용했다.

| 항목 | 값 |
|---|---:|
| 종목 | 35 |
| 5m bar | 673,135 |
| 60m bar | 70,034 |
| 기간 | 2025-05-15 ~ 2026-05-26 |
| 비용 | 왕복 33bps(0.33%) |
| 미체결 역선택 | 상위 수익 후보 5% 제외 |

분석 흐름은 2개다.

| 흐름 | 설명 | 후보 수 |
|---|---|---:|
| Raw 5m Agent Council | 기존 5분봉 `AGENT_COUNCIL` BUY | 62,719 |
| MTF 5m+60m Council | 5m `AGENT_COUNCIL` BUY 중 60m `AGENT_COUNCIL`도 BUY인 후보 | 24,664 |

주요 판정은 MTF 5m+60m Council 기준으로 한다. 최근 연구에서 가장 나았던 흐름이고, raw 5m는 민감도 확인용이다.

한계: 이 분석은 signal-level forward-return이다. 실제 계좌의 max position, 1 tick 신규 진입 제한, 체결 지연, stop-loss 체결 순서는 포함하지 않는다. 같은 timestamp의 여러 종목 후보는 시간순/종목순으로 정렬했다. timestamp 단위 평균 bucket으로 재검산해도 결론 방향은 같았다.

순손익만 보면 3패가 가장 크지만, 너무 자주 발동해 31.5%의 후보를 제거한다. 5패는 제거 비율이 19.6%이고, skip된 후보 평균이 기준 평균(-0.2706%)보다 훨씬 나쁜 -1.0069%다. 즉 무작위 거래감소가 아니라 연패 이후 후보가 실제로 더 나빴다.

## 6. 5패가 정말 신호인가

그렇다. MTF 기준 5연패 후:

- 다음 1개 거래 평균: `-0.6682%`
- 다음 1개 거래 승률: `20.00%`
- 다음 5개 거래 평균: `-0.7510%`
- 다음 5개 window가 양수인 비율: `11.24%`
- `skip_next_5`로 실제 제거된 후보 평균: `-1.0069%`
- 기준 전체 평균: `-0.2706%`

한국장이 reversal 성격이 있다는 우려와 반대로, 이 신호열에서는 연패 후 반등이 아니라 **동조 손실 지속**이 더 컸다. 좋은 반등을 놓친 거래도 있다. 하지만 skip된 후보 승률은 `12.48%`뿐이라 손해보다 방어 효과가 압도적이다.

## 7. 손절/일일손실가드와 중복인가

부분 중복은 있지만 대체관계는 아니다.

- 손절은 개별 포지션의 하방 제한이다. 연패 차단은 신규 진입 자체를 줄이는 market/signal health guard다.
- 일일손실가드는 금액 기준이다. 계좌 크기, 주문 크기, 이미 실현된 손익에 의존한다.
- 연패 차단은 금액이 작아도 "후속 후보가 나쁜 상태"를 감지한다. 이번 데이터에서는 금액 기준보다 앞서 작동할 가능성이 있다.
- 다만 코드에는 이미 `ConsecutiveLossRule`이 있으므로 **신규 모듈 추가는 중복**이다. 필요한 것은 활성화 경로, finite cooldown, reset 정책, UI/로그 표면화다.

## 8. 권장 설계

운영 후보:

```text
threshold: 5 consecutive losing closed trades
action: block new BUY only
cooldown: next 5 BUY candidates, or 30~60 minutes if candidate count is unavailable
reset: cooldown 만료 시 streak=0
scope: account-level first, per-strategy/per-symbol은 추후
SELL/EXIT: always allowed
logging: circuit_breaker_triggered, threshold, skipped_count, last_loss_trade_ids
```

추가 안전장치:

- 무기한 차단 금지. 실제 거래가 멈추면 closed trade가 추가되지 않아 streak가 풀리지 않는다.
- emergency stop과 분리. 연패 차단은 L1 신규매수 중단이고 emergency stop은 상위 hard stop이다.
- 첫 적용은 shadow/paper only. 실제 봇 적용 전에는 실제 체결 로그로 "연패 계산이 언제 확정되는가"를 확인해야 한다.
- 현재 `RiskPolicy.from_settings()`에는 `consecutive_loss_limit`가 settings에서 주입되지 않는다. 실제 적용 시 이 wiring을 명확히 해야 한다.
