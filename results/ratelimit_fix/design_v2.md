### 1-2. 07-09에 4,034까지 튄 트리거

단발성 "재시도 폭풍" 하나가 아니라 **상시 구조적 오버부킹**이다. 서로 독립된
3개의 폴링 루프가 *동일한 단일 공유 rate limiter*(`get_kis_rate_limiter()`,
프로세스 전역 singleton, `kis_rate_limit_calls=1`/`window=1.1s` ≈ 0.9회/초)
예산을 나눠 쓴다:

1. **프론트 대시보드** (`usePortfolio.js`) — `PRICE_TICK_MS=15000`(15초)마다
   `Promise.allSettled([brokerBalance(), ...codes.map(brokerPrice)])`를
   **동시 발사**. `codes` = 보유종목 전부(`runtime_overrides.json` 기준
   `max_concurrent_positions=15`, 현재 실측 8건).
2. **봇 자체 스캔** (`driver_bridge.py`) — 매 30초 틱마다 회전 슬라이스
   (`kis_paper_scan_max_symbols` 기본 10, cap 30) + **보유종목 union**(청산
   보장을 위해 매 틱 강제 포함)만큼 quote 조회.
3. **FillPoller** — 별도 `kis_paper_fill_poll_interval_seconds=10`초 주기로
   미체결 주문의 daily-ccld 상태를 독립적으로 폴링.

이 셋은 **서로의 스케줄을 모른다** — 리미터가 "지금 누가 먼저 왔나"만 보고
순서대로 통과시킬 뿐, 총 수요가 공급(0.9회/초)을 넘으면 뒤로 밀리는 요청이
계속 쌓인다. 정량 확인(프론트만 단독으로):

- 프론트 1틱 = 1(balance) + N(price), N=보유종목수.
- 리미터로 순서대로 처리하는 데 필요한 시간 ≈ (1+N) × 1.1초.
- **N=8(현재 실측)일 때 9.9초 — 15초 폴링 주기 안에는 들어가지만, 이미
  예산의 66%를 프론트 혼자 씀.** N이 12 이상이면 (1+N)×1.1s ≥ 14.3초로
  15초 주기에 육박/초과 — **다음 폴링 틱이 이전 틱을 다 처리하기도 전에
  도착**해 영구적으로 밀린 요청이 쌓이는 구조가 된다. 여기에 봇 스캔(틱당
  10~25종목)과 FillPoller(10초 주기)가 **동시에** 같은 예산을 요구하므로,
  보유종목이 적어도(N=8) 셋을 합치면 이미 초당 처리량을 넘기기 쉽다.
- 07-09가 07-10보다 거의 2배 높았던 것도 이 모델과 일치한다 — 보유종목 수
  변동(체결로 늘거나 줄면 N이 바뀜) + 장중 체결 빈도(FillPoller가 더 자주
  도는 종목 수)가 그날그날 수요를 크게 흔든다. **"어떤 한 사건"이 튄 게
  아니라, 매일 수요가 공급 근처/초과를 오가는 상태이고, 그날의 보유종목
  구성·체결빈도에 따라 오버부킹 정도가 달라지는 것으로 보인다.**

### 1-3. `a92a59d`(stale-fallback)가 왜 효과 없었나

커밋 자체 코멘트가 정확히 설명한다(`routes_broker.py`):

> "프런트 대시보드(usePortfolio.js)가 15초마다 보유종목 전부를 Promise.all
> 로 동시 조회하는데, 예외 없이 그대로 두면 레이트리밋 실패가 매 틱 배치
> 전체 재시도를 유발해 봇 자신의 회전 스캔과 경합을 키운다"

이 커밋은 **"실패했을 때 UI가 또 실패를 유발하는 연쇄"**(Promise.all의
all-or-nothing 재시도)를 끊었다 — `Promise.allSettled`로 바꿔 한 종목
실패가 잔고까지 같이 버려지는 걸 막고, `/broker/price`가 실패 시 stale
캐시를 200으로 반환해 프론트가 재시도를 안 하게 만들었다. **그런데 이건
"실패 후 재시도"를 줄인 것이지, "애초에 보내는 요청 수"는 그대로다** —
매 15초마다 1+N개 동시 요청을 쏘는 기본 패턴 자체는 변경 안 됨. 그래서
성공/실패와 무관하게 매틱 여전히 같은 양의 부하가 발생하고, EGW00201
발생률도 거의 그대로였다.

## 2. order-cash(주문)/balance(잔고) 조회가 왜 많나

**전제가 틀렸다 — order-cash는 12건/6,181건(0.2%)으로 거의 안 나온다.**
아래는 balance(12.5%, 실제로는 2위)에 대한 답.

- **주문마다 잔고 재확인?** `order_router.route_order`가 평가 직전 매번
  `quote`+`balance`+`positions` 3종을 조회한다(코드 확인, `order_router.py`)
  — 그런데 이건 **실제 BUY/SELL 시도가 있을 때만** 호출된다. `driver_bridge.py`
  는 HOLD 신호면 `route_order`를 호출하지 않고 `HOLD_NO_SIGNAL`로 스킵한다
  (확인됨) — 매 틱 전종목마다 balance를 재확인하는 구조는 아니다.
- **중복 조회?** 프론트가 15초마다 `brokerBalance()`를 1회 호출(보유종목
  수와 무관하게 항상 1콜) — 이게 balance 부하의 주된 반복 소스로 보인다.
  KIS 어댑터 자체엔 `kis_balance_cache_ttl_seconds=20`(20초) 캐시가 있어
  15초 폴링과 살짝 어긋난다(폴링 주기 < 캐시TTL이라 대부분은 캐시 히트여야
  정상이지만, 봇의 자체 balance 조회 타이밍과 위상이 어긋나면 캐시 미스가
  주기적으로 겹칠 수 있다 — 정밀 확인은 로그만으론 어렵고 라이브 계측 필요).
- **프론트 폴링인가 봇 내부인가?** **압도적으로 프론트**(1-2 참고). 봇
  내부는 실제 매매 시도(하루 수십 건 규모, 06-08 조사와 유사 규모로 추정)
  일 때만 발생 — 상시 폴링 주체는 프론트다.
- **naked SELL 차단 로직이 매번 잔고 조회하나?** `routes_manual_order.py`
  의 naked-SELL 가드(`broker.get_positions()`)는 **수동주문 API 전용**이고
  **사용자가 실제로 SELL 버튼을 누를 때만 1회** 발생한다 — 폴링이 아니다.
  상시 부하에 대한 기여는 무시 가능한 수준.

## 3. 대응 방향 (★손절 사수 원칙)

**손절/청산 실시간 조회(`app.market_data.kis_realtime.fetch_realtime_quote`)는
이미 `/broker/price` 라우트·프론트 캐시와 분리된 별도 경로다**(a92a59d 코멘트
확인) — 코드 경로 자체는 안전 분리돼 있다. 다만 **같은 프로세스의 같은 단일
rate limiter(`get_kis_rate_limiter()`)를 공유**하므로, 프론트/스캔 트래픽이
예산을 채워버리면 손절 판단의 실시간 조회도 대기열에 밀려 EGW00201 확률이
같이 올라가는 **간접 리스크**는 남는다 — "경로는 분리, 자원은 공유"가 정확한
현재 상태.

권고(신규진입·표시용 조회만 throttle, 청산 경로는 건드리지 않음):

1. **프론트 폴링 요청 수 자체를 줄인다** — 우선순위 1위. `usePortfolio.js`가
   보유종목마다 개별 `brokerPrice` 호출을 동시발사하는 대신:
   - (a) 다종목 일괄조회 백엔드 엔드포인트 신설(`/broker/prices?symbols=...`)
     → N콜을 1콜로 축소(리미터 소모 N분의1). *KIS API 자체가 다종목 일괄
     시세를 지원하는지 확인 필요 — 미지원이면 백엔드가 내부에서 여전히
     N번 KIS를 부르지만 최소한 프론트↔백엔드 왕복은 줄고, 백엔드가
     자기 스캔 사이클에 맞춰 batching/staggering할 여지가 생긴다.
   - (b) 그게 어려우면 프론트에서 N개 요청을 동시발사 대신 100~200ms
     간격으로 staggering — 리미터 대기열에 한번에 몰리는 걸 완화.
2. **폴링 주기를 캐시 TTL과 정렬** — `PRICE_TICK_MS`(15s) < 캐시TTL(20s)
   구조 자체가 낭비다(대부분 재조회해도 어차피 캐시가 아직 유효한 시점에
   또 조회 시도). 폴링을 20~25초로 늘리면(대시보드 신선도는 소폭 저하,
   트레이드오프 명시) 캐시 히트율이 오르고 실제 KIS 호출은 줄어든다.
3. **봇 스캔·프론트 폴링에 "낮은 우선순위" 백오프** 적용 — EGW00201을
   맞은 quote/balance 요청(표시·스캔용)은 짧은 지수 백오프 후 포기(다음
   틱에 재시도)하도록, 반면 `fetch_realtime_quote`(청산 판단)는 현재처럼
   즉시·최우선으로 시도 — 이 구분이 코드상 이미 경로는 분리돼 있으니
   **우선순위 큐/게이트를 limiter 앞단에 추가**하는 정도로 구현 가능
   (설계만, 미구현).
4. **FillPoller 주기(10초)도 재검토** — quote/balance만큼은 아니지만
   daily-ccld가 6.8%를 차지. 미체결 주문이 없을 때는 폴링을 건너뛰거나
   더 긴 주기로 늦추는 여지 확인.

조회 경로(`fetch_realtime_quote`)는 그대로 유지하거나(우선순위 큐 적용 시)
오히려 자원 경합에서 더 보호받는 방향.

## 5. 한계 (정직히 명시)

- 이 문서는 **로그 실측 + 코드 경로 추적**이며, 실시간 계측(예: 실제 요청
  타임스탬프를 요청-소스별로 tagging해 정확한 비율 확인)은 하지 않았다 —
  "프론트 폴링이 지배적"이라는 결론은 코드 구조(폴링 주기·동시발사·N값)의
  정량 추정이지, 실제 트래픽을 소스별로 라벨링해 직접 센 것은 아니다.
- EGW00201 실패 로그의 밀리초 단위 간격 일부가 이론상 리미터 최소 간격
  (1.1초)보다 짧게 관측됐다(예: 0.78~0.88초 간격) — 응답 도착 순서가 실제
  발신 순서와 다를 수 있는 비동기 특성 때문일 가능성이 높지만, 완전히
  배제하려면 발신 시점 자체를 로깅해야 한다(현재 로그는 응답/실패 시점만
  기록). 리미터 구현 자체의 버그 가능성은 낮게 보지만 100% 배제는 못 했다.
- KIS 계정의 실제 초당 한도가 정확히 몇인지는 여전히 모른다(0.9/초로도
  실패가 나는 걸 보면 그보다 낮을 가능성) — 공식 문서/고객센터 확인이
  가장 확실하나 이 조사 범위 밖.
